## About

I work across the stack — Java/Spring Boot on the backend, React on the front, Postgres underneath, Docker to ship it — but the part I actually care about is the layer most people skip: what happens when the happy path breaks. Cascading service failures, log redirection through systemd/journald, JVM startup diagnostics, network/port requirements that only surface in production. I'd rather spend an afternoon tracing a root cause through logs than patch the symptom and move on.

Right now that shows up in two places: shipping full-stack systems from scratch, and doing the unglamorous work of turning tribal knowledge into structured, reusable documentation — SOPs, requirement checklists, rollback procedures — because undocumented systems are technical debt that just hasn't been billed yet.

```yaml
currently:
  building:   [VoltBill, SparkIn, JustExam v2]
  studying:   [Spring Cloud microservices, distributed systems, system design]
  refining:   [production-grade backend architecture, database performance]

principle: "Understand the system before you extend it. Document it so the next person doesn't have to."
```

## Selected Work

**VoltBill** — Billing platform for retail shops.
`Spring Boot 3.2` `Java 17` `React 18 + Vite` `PostgreSQL (Supabase)`
Built around getting invoicing and inventory logic correct first, UI second — the kind of app where a rounding error is a real complaint from a real shop owner.

**SparkIn** — Full-stack blogging platform, built end-to-end during an IBM internship.
`React 19` `Node.js` `Express 5` `MongoDB` `Tailwind`
JWT auth, a TipTap-based editor, comment threads, moderation tooling. The scope was small; the goal was to get the boring parts (auth, permissions, data modeling) genuinely right.

**JustExam** — Online examination system, currently being refactored rather than rewritten.
`PHP` `MySQL` `JavaScript` `Bootstrap 5`
Role-based access, real-time exam delivery, automated grading. Revisiting an older codebase to fix its architecture is a different skill than writing a new one, and I think it's the more instructive one.

## How I Work

I lean on tooling to remove repetitive work rather than to avoid understanding it — n8n pipelines connecting Sheets → summarization → WhatsApp delivery, Excel-based WIP tracking with real status logic, Python/Node scripts that generate structured docs instead of hand-formatting them every time. The goal isn't automation for its own sake; it's fewer places for manual error to creep in.

```javascript
const approach = {
  debugging: "logs before assumptions",
  docs: "written once, reused always",
  new_tech: "read the internals, not just the API",
  refactors: "understand why it was built that way first",
};
```
